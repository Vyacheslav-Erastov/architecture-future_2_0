# Обоснование перехода на событийно-ориентированную архитектуру

## Текущая ситуация (проблемы с Camel и DWH)
- **Монолитное DWH**: вся бизнес-логика и данные сосредоточены в одном хранилище. Любое изменение требует долгих циклов согласования и тестирования. Формирование сложных отчётов занимает часы.
- **Шина Camel**: обеспечивает интеграцию, но часто синхронную или с жёсткими маршрутами. Добавление нового потребителя данных требует изменения маршрутов и переразвёртывания.
- **Высокая связанность**: системы зависят друг от друга через общую БД и шину, что замедляет внедрение новых фич и масштабирование.
- **Time-to-market**: на построение отчётности уходят недели, аналитики ждут данных.

## Преимущества событийного подхода (Event-Driven Architecture)

### 1. Слабая связанность
- Домены общаются только через события, не зная о внутренней структуре друг друга. Это позволяет развивать каждый домен независимо.
- Новые подписчики могут добавляться без изменения кода источника - достаточно подписаться на нужные топики.

### 2. Масштабируемость
- События обрабатываются асинхронно, каждый сервис может масштабироваться горизонтально независимо.
- Брокер событий (Kafka) легко масштабируется под растущий объём данных (в перспективе near-real-time).

### 3. Скорость реакции
- События доставляются практически мгновенно. Например, после завершения приёма сразу генерируется событие `AppointmentCompleted`, которое триггерит выставление счёта и обновление статистики.
- Возможность строить потоковые аналитические витрины (Kafka Streams, Flink), что позволяет получать актуальные данные в реальном времени, а не раз в сутки.

### 4. Надёжность и согласованность
- Использование брокера с гарантиями доставки (at-least-once, exactly-once) и DLQ для ошибочных сообщений повышает отказоустойчивость.
- События хранятся в логе, что позволяет воспроизвести состояние системы на любой момент (аудит, отладка).

### 5. Гибкость интеграции новых бизнес-направлений
- При подключении фармацевтической компании или производителя оборудования новый домен просто начинает публиковать свои события и подписываться на нужные. Не требуется переделывать существующие интеграции.
- Соответствует принципам Data Mesh: каждый домен владеет своими данными и публикует их как продукты.

### 6. Соответствие стратегическим целям
- В долгосрочной перспективе компания планирует перейти к слабосвязанной событийной платформе. Событийная архитектура - фундамент для этого.
- Позволяет реализовать near-real-time обработку данных, что важно для мониторинга и оперативной аналитики.

## Сравнение с текущим подходом
| Критерий               | Camel + DWH                          | Event-Driven + Data Mesh                |
| ---------------------- | ------------------------------------ | --------------------------------------- |
| Связанность            | Высокая (общая БД, жёсткие маршруты) | Низкая (только события)                 |
| Скорость изменений     | Низкая (любое изменение требует ETL) | Высокая (независимые домены)            |
| Производительность     | Падает с ростом данных               | Линейно масштабируется                  |
| Актуальность данных    | Batch (раз в сутки)                  | Near-real-time                          |
| Стоимость поддержки    | Высокая (легаси)                     | Средняя, но снижается за счёт автономии |
| Соответствие Data Mesh | Нет                                  | Да (основа)                             |

Таким образом, переход на событийную архитектуру критически необходим для достижения целей бизнеса по масштабированию, скорости вывода новых продуктов и повышения качества аналитики.
